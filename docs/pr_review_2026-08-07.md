## #419 — `split/doc-count-autofix`

**Verdict: no blocking findings. I have independent live evidence FOR it, from a
different code path than the one he debugged.**

### What it fixes

`--fix` had fixers for tests, hooks and the architecture tree, and **none for
command counts**. So on command-count drift it ran, changed nothing, and the
caller printed *"still drifted after auto-fix (likely a non-count error).
Investigate manually."* It IS a count error — it simply had no fixer, and the
message misdirected everyone who read it.

He also adds `--allow-lower`, because the monotonic guard has a hole all three
fixers shared:

```python
if actual <= max_existing and not allow_lower:
    continue          # fixer refuses to lower
```

…while the **checker still errors on documented > actual**. Fixer and checker
disagree, so a doc that overclaims can never converge — the tool refuses to do
its job and tells you to do it by hand.

### My evidence, and why it strengthens the PR

I hit this **today**, in this session, and hand-edited the number exactly as he
describes — before I had read his PR.

```
README.md documented : 109 hooks
actual               : 104
`--fix`              : reported the drift, changed nothing
what I did           : edited README by hand
```

Tested his branch's guard against my real numbers:

```
allow_lower=False  ->  guard skips the fix   (the bug I hit)
allow_lower=True   ->  guard does not skip   (fixed)
```

**The part worth noting for the review:** my case was in the HOOK fixer, not the
command fixer. He found the hole while debugging the missing *command* fixer;
my instance shows the same hole in a fixer that already existed. His change
covers it because he threaded `allow_lower` through **all three** rather than
only the one he was working on. That is a wider fix than the bug that prompted
it, and it turned out to be necessary.

### Wiring verified, not assumed

The failure mode I keep finding this week is a mechanism defined and never
called. Checked:

```
720  allow_lower = "--allow-lower" in sys.argv        flag parsed
785  fix_test_counts(...,    allow_lower=allow_lower) threaded
797  fix_hook_counts(...,    allow_lower=allow_lower) threaded
807  fix_command_counts(..., allow_lower=allow_lower) threaded
543  def fix_command_counts                            defined
807  fix_command_counts(...)                           CALLED
```

All three fixers take it; the new function is defined *and* invoked.

### Design notes, not objections

- **Monotonic stays the default.** `--allow-lower` is opt-in, so the
  2026-06-12 rule (branches must not fight over the same line at rebase)
  survives. Correct call — making lowering automatic would trade one recurring
  annoyance for a rebase conflict nobody could see coming.
- **The fixer reuses the checker's regex shape** (`(\d+)(\s+(?:CLI\s+)?commands)`)
  so the two cannot disagree about what counts as a mention. That is the
  two-place defect closed at the point it would otherwise open.

### Open question for him, non-blocking

The `--allow-lower` escape is manual. Nothing tells the operator it exists at
the moment they need it — the failure message still says *"Investigate
manually."* Naming the flag in that message would close the loop from
gate-to-remedy, which is the seam class he named this morning: **a mechanism
whose documented remedy has drifted from what the mechanism can do.**

I have not changed his message. It is his PR.
