# The merge gate refuses a merge that is behind main

**Written:** 2026-10-18, night. **Branch (to be):** `aether/merge-gate-refuses-a-behind-merge`.

## Why this exists

Aletheia, 2026-10-18, on the stamp retirement (#691): the stamp's refusal of a branch that is behind main was, without anyone having said so, the only thing stopping a behind branch from merging on checks that ran against an older main. I claimed GitHub's own rule covered it. I measured, and it does not: the ruleset "main protection" requires `multi-party-review`, `test (3.12)` and `test (3.12, sklearn)` but has `strict_required_status_checks_policy: false`, so GitHub does not require a branch to be up to date before merging. Her condition, in her words: land #691 only once one replacement is in place. The two replacements she named are this refusal (mine to build) or Dad switching the strict policy on (his call). Either is enough.

## What it does

`gh pr merge N` is already refused by `core/pr_merge_gate.py` when the PR touches a guardrail file and the command has no review trailer. This adds a second, separate refusal that applies to every merge: if the PR's head does not contain main's tip, the merge is refused with the remedy. GitHub's compare endpoint answers it (`behind_by` for `main...<head>`), and the remedy is `gh pr update-branch N`, which merges main into the PR branch on GitHub's servers and reruns the required checks there, so it costs no local test suite and no new signature (the stamp's content rung follows the change, not the floor).

"Behind main by any amount" is the safe stand-in for Aletheia's "checks ran against a different main", not the same question: if the head already contains main's tip the check saw the latest main, and if it is behind the check may still have run on a newer one, so the gate can refuse a merge that would have been fine. That error costs one `update-branch` and a rerun and runs in the safe direction; the exact question would need a guess about timestamps, which is worse.

Three states, kept apart on purpose: fresh (merge may proceed), behind (refused, remedy named), could-not-look (refused, saying so, because an unreadable check must not read as a pass; a merge needs the network anyway).

## The reading is shared, in its own module (Aletheia's hold on #692, 2026-10-18)

Aletheia held #692 at `d8364726b` for two doors it did not watch: the GitHub API's direct merge (`gh api -X PUT repos/<o>/<r>/pulls/<N>/merge`, also `--method PUT`, `--method=PUT` and `-XPUT`, with or without `-f merge_method=squash`, which merges without `gh pr merge` ever appearing) and the program named by a path (`/usr/bin/gh pr merge N`). Both are closed, and not inside this gate. What a command merges is read once, by `core/merge_command.py` (`merge_targets`), which returns every merge the command performs as a pull request, a repository and a route (`pr` or `api`); `merge_freshness` only asks GitHub about each one. The reason is measured: the existing review gate beside this one, probed with a stand-in guardrail lookup (PR 99 touches a guardrail file, no review line), catches only the plain `gh pr merge 99 --squash` and ALLOWS `--squash 99`, `/usr/bin/gh pr merge 99`, both API spellings, and the chained pair. Three gates with three private patterns is how one hole becomes three, so the next change points that gate at the same reader.

STILL NOT SEEN, and named so silence is not read as coverage: a merge from the web page's button, a merge through the GraphQL API (`mergePullRequest`), the same REST call made by another program (`curl -X PUT https://api.github.com/repos/<o>/<r>/pulls/<N>/merge`, or a script that calls it), a merge launched from inside a quoted string of another language (`python -c "subprocess.run(['gh','pr','merge','42'])"`), a program whose path is quoted because it contains a space, and a merge typed from a folder that is not the repository. The reader finds merges by `gh`'s own vocabulary; a different program that talks to GitHub is a different door, and only the ruleset's strict policy, which GitHub enforces whichever program asks, closes all of them. Probed and seen: a merge inside a heredoc script fed to `bash`, a quoted API endpoint, an API call with its body on stdin, a trailing `--jq`, extra spaces and an environment prefix, a merge after `gh pr review --approve &&`, and text that only mentions a merge inside a commit message or another command's body. If Dad switches on the ruleset's strict policy, GitHub refuses a behind merge through every one of these doors, and this gate becomes the explanation of the remedy and not the only lock.

## What it does not do

It does not run `update-branch` for me (that is the automation a later doorman could add; per Dad's rule a gate-fire is a finding, not a save). It does not prove the merged result is green: after `update-branch` the checks rerun and the gate asks again at merge. And if main moves again in between, it refuses again; that costs a rerun, never a signature.

WHICH MERGES IT SEES. Aria tried twelve shapes and found the first version asked only when the number came straight after `merge`, so `gh pr merge --squash 42`, the most ordinary way to type it, went ungated. It now reads the pull request as whatever `gh pr view` accepts: a number, `#number`, a URL, a branch name, or nothing at all (which `gh` reads as the pull request of the checked-out branch), with flags allowed before it and the flags that take a value skipped together with their value. Every merge in a chained command is read, not just the first: probing the parser for the walk showed `gh pr merge 1 && gh pr merge 2` asked only about the first, so a stale second PR would have ridden behind a fresh one (the existing merge gate beside it takes only the first match as well). A repository named with `-R` or `--repo` (before or after the pull request, or as `--repo=name`) is read and passed to both GitHub calls, instead of being mistaken for the pull request (Aria's second read of #692). The words of the command are read from the original text, split the way a shell splits them, and the quote-scrubbed copy is used only to find where the command ends, because the scrubber blanks quoted values (a quoted `-R "o/r"` became spaces); and because that text now reaches `gh` and an API path, a repository is accepted only as `owner/repo` or `host/owner/repo` with no `.` or `..` part, and anything else is refused as could-not-look before `gh` is asked. Values of flags that take one are skipped even when quoted, because the quote-scrubber leaves a blank placeholder token in their place, which was checked rather than assumed. What it still does not see is a merge from the web page's button, which is outside every local gate, and a merge made from a folder that is not the repository. The existing merge gate beside it has the old number-first pattern and so has the same hole for its review check; that is a separate finding, below. Measured against real GitHub on 2026-10-18, not just a stand-in: #691 read as 0 behind, #659 as 3 and #592 as 50, and plain `git rev-list --count` agreed on the two it could reach (3 and 0). A merge costs about 1.3 seconds for the two `gh` calls; a command that is not a merge costs nothing.

## Does a review survive `update-branch`? (Aria's cold read, 2026-10-18)

The remedy sentence said a stamped PR's review "still holds" after `update-branch` and nothing pinned it. What is shown, and what is not:

- **From the code.** `scripts/ci_check_guardrail_trailer.sh` reads the trailer from the PR body and, on that path, blanks the tree-hash ("describes the PR, not this commit; not verified here"), so a new head does not break the required check `multi-party-review`. `scripts/ci_merge_review_check.py` (the `merge-review` job, not one of the three the ruleset requires) exits 0 for PENDING, meaning "nobody has approved the current head yet", which is the state of every freshly pushed head; its header says that making it fail was measured to make it unpassable.
- **From real PRs today.** #673, #674, #678 and #681 each had their head moved (a merge of main) after Aletheia's confirm was given, were stamped on the later head by the content rung, and merged with all required checks green. A merge of main into the branch is exactly the commit `update-branch` makes.
- **Not shown.** A literal `gh pr update-branch` on a stamped PR followed by its merge. The first real use will be that case, and this note names it so it is watched, not assumed: if the required checks or the merge-review job refuse a stamped PR after `update-branch`, the remedy this gate names is wrong and the gate must change.

## How we would know it failed

A behind PR merges, or a fresh PR is refused, or a stamped PR that was brought up to date with `update-branch` is refused by a review check. The first is the thing this exists to stop; the others mean the reading or the remedy is wrong.
