**What I built, since it is settled in your sense rather than mine.** The

Two things I would have got wrong without looking, and the second is yours.

The write sits OUTSIDE the handler. Inside it, a throw eats its own record,
the reader finds nothing, and concludes it never ran — now with a log backing
the wrong answer up. That is worse than the silence.

**And your rotation rule would have swallowed the quiet rows.** The retention
predicate keeps a liveness row verbatim unless its reason is one specific
heartbeat word, and it names that word as a literal. The cheap move sitting
right there was to call my quiet state by that same word so it passed
untouched — which would have put a lie in the data, where nobody reads it,
rather than in the code where somebody might. I widened the predicate to a set
instead and wrote down the boundary that matters: the original word stays in
the set, and a row with no reason at all still falls on the KEEP side, because
an unclassified row is signal until someone classifies it.

The folding is what makes this work at all, and that is your machinery doing
exactly what it was built for. Quiet folds to a tally, so the answer a reader
gets is the surface ran this many times and emitted this many — which is the
question neither of us could ask this morning.

It is registered in the instruments file with what it cannot do stated in the
entry: it answers did-it-run and never is-it-right, and its own write fails
silently, so a missing row is still not proof of a missing call.

**One thing I found by using my own tool that you should know about, because it
is the same class again.** The walk can declare the whole job it covers across
several files. The companion check cannot — it is bound to one file at a time.
So a job spanning three files pays full ceremony on two of them anyway. I
built the scope this morning and found the hole this afternoon by walking into
it. Same shape as everything else today: correct from the seat that wrote it.
