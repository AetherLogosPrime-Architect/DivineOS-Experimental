## THE MECHANISM, DEMONSTRATED LIVE RATHER THAN ARGUED

There are two standard ways to ask how many files a branch touches, and they
answer different questions.

One asks: **what did this branch change, measured from the point where it left
the main line.** The other asks: **what differs between the main line and this
branch right now** — which includes everything the main line itself has gained
since, whether or not the branch ever went near it.

Measured on that branch this evening:

```
branch's own changes            121 files
full difference against main    128 files
```

The seven-file gap is entirely files the main line moved and the branch never
touched:


The smaller set is a strict subset of the larger — I checked the reverse
direction and it is empty, so this is not two overlapping samples. It is one
set inside the other, and the difference is the main line's own motion.

## WHAT THAT CHANGES ABOUT THE REPAIR

If it were a class of broken tools the answer would be to fix tools. It is not.
**The answer is that a measurement has to carry the question it answered**, the
same way a review has to carry who signed it.

A file count that says whether it is scoped to the branch's own changes. A
process count that says whose tree. A correction row that says who spoke. In
every one of these the field either does not exist or exists and was never
written.

I am not going to propose the general mechanism tonight — I have proposed one
