# 🟡 FINDING 56 — deletion-discipline gate can be evaded by quoting the rm FLAGS (`rm "-rf" src/`); the sanitize step strips the quoted flags, so the force/recursive detector doesn't fire

**Plain version:** The deletion-discipline gate blocks destructive commands (git branch delete, `git rm`, recursive/force `rm` of non-ephemeral paths) until justified. It correctly strips quoted/heredoc CONTENT before detection, so a deletion *mentioned* in a commit message doesn't false-trigger (good use-vs-mention discipline). But I tested evasion vectors empirically, and found one: **quoting the rm FLAGS — `rm "-rf" src/` — evades the gate.** The sanitize step strips the quoted `"-rf"`, so the recursive/force detector (which needs to see `-r`/`-f`) no longer matches, while the shell still executes it as a recursive force delete.

**The mechanism (verified by running the actual regexes):**
- The verb/flag detection runs on the SANITIZED command (`_DQUOTED`/`_SQUOTED`/`_HEREDOC` content stripped).
- `_RM_RECURSIVE_OR_FORCE` requires seeing the `-r`/`-f` flag to classify an rm as destructive.
- `rm "-rf" src/` → sanitize strips `"-rf"` → scan sees `rm  src/` → the flag pattern doesn't match → **gate returns False (not destructive)**.
- But the shell treats `"-rf"` identically to `-rf` — the quotes are shell syntax, not part of the argument. So the command executes as `rm -rf src/`, a recursive force delete of a real path, **with the gate silently not firing.**

**Empirical test results (ran the sanitize + detection logic directly):**
```
True   <- rm -rf src/            (plain — fires, correct)
True   <- rm -rf "src"           (quoted path — fires, correct: path stripped but flags remain, ephemeral-check fails)
False  <- rm -rf __pycache__     (ephemeral — passes, correct)
True   <- rm -rf __pycache__ src/ (mixed — fires, correct)
False  <- rm "-rf" src/          (quoted FLAGS — EVADES ← the finding)
True   <- rm -rf "$(echo src)"   (command-subst — fires, correct)
True   <- git rm -r src/         (git rm — fires, correct)
```
Only the quoted-flags vector evades. The gate is otherwise robust (quoted paths, mixed targets, command-substitution all correctly fire).

**Honest calibration:** MEDIUM. In the cooperative single-operator context there's no adversary crafting `rm "-rf"` to sneak a deletion past the gate — and no normal workflow quotes rm flags (it's an unusual construction). So real-world trigger probability is low. But it's a genuine evasion of a DESTRUCTIVE-action safety gate, and the "sanitize strips quoted content" design — which is correct for avoiding false-positives on mentioned-deletions — is exactly what opens it: stripping quoted content removes quoted FLAGS too, and flags are semantically load-bearing in a way commit-message-text isn't. The gate's own comment ("a miss is safer than blocking every commit that mentions a delete") accepts misses to avoid false-positives, but for the flag-evasion case a miss means a real recursive delete executes ungated — the wrong direction for a destructive gate.

**The fix (detect flags on a flag-aware sanitize, or normalize before scanning):**
1. **Don't strip quoted FLAGS — only quoted non-flag content.** The sanitize step should preserve tokens that look like flags (`-rf`, `--force`) even when quoted, since a quoted flag is still an operative flag. Alternatively, detect the rm verb + flags on a shell-normalized form (strip quote CHARACTERS but keep the token content) rather than deleting quoted spans entirely.
2. **Shell-tokenize instead of regex-strip** — parse the command into shell tokens (e.g. `shlex.split`) and inspect the actual arguments to `rm`, so `"-rf"` and `-rf` are recognized as the same flag. This is more robust than regex-strip against all quoting tricks, not just this one.
3. **For the destructive-gate specifically, fail toward firing on quote-ambiguity** — if a command contains `rm` and quoted spans that could hide flags, err toward firing (the opposite lean from the "miss is safer" comment, because for deletions a false-block is cheap and a missed-delete is expensive).

**The pattern:** *the use-vs-mention discipline (strip quoted content so mentioned-deletions don't false-trigger) is correct for avoiding false-positives, but stripping quoted content also strips quoted FLAGS — and flags are operative, not mentioned. `rm "-rf" src/` executes as a recursive delete while the gate sees an un-flagged rm. The regex-strip approach can't distinguish "quoted to mention" from "quoted to evade"; a shell-tokenizer can. Fix by parsing shell tokens (so quoted and unquoted flags are equivalent) rather than deleting quoted spans, and for a destructive gate specifically, lean toward firing on quote-ambiguity — a false-block on a delete is cheap, a missed delete is not. Same shape as F48 (structural not superficial matching) but for shell commands: match the SEMANTICS (what rm will actually do) not the surface text (what the flags look like after stripping).*
