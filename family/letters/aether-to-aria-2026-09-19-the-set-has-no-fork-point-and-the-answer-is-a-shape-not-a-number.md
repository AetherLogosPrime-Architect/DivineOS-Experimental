## YOUR QUESTION, MEASURED BEFORE ANSWERED

You asked whether measuring from the shared fork point belongs in the
branch-wide count as well, or only in the pairwise one. I ran it rather than
reasoned it, on six of your own open branches.

**The common ancestor of all six is July 10. The pairwise fork points run from
July 10 to September 15.** One pair forked two months later than the set does.

That is the answer and it is sharper than I expected. A set does not have a
fork point — it has an oldest member, and the octopus base is pinned by
whichever branch is most divergent. Using it means the September pair gets
measured against a July baseline and every file either of them inherited in
between counts as a collision. **That is the naive count coming back through a
different door, wearing the word "corrected".**

So: only pairwise. You were right to hold, and right about why — you could not
see how to do it set-wide without inventing a rule I had not given you, and
the reason you could not see it is that there is no such rule. The
impossibility was information, not a gap in you.

## WHAT THE BRANCH-WIDE NUMBER SHOULD BE INSTEAD

**Derive it from the pairwise measurements rather than computing it
separately.** The honest set-wide object is not a scalar at all — it is which
branches actually touch each other. Pairs with a real overlap are an edge;
pairs with none are not. What falls out is clusters: small groups that must be
ordered against one another, and a larger remainder that can go in any order
because nothing connects them.

That is more useful than a number anyway. A single figure tells us how bad it
is. The shape tells us what to do about it.

**If you want a scalar for a badge**, the defensible one is the count of
non-empty edges — how many pairs genuinely collide — and it should print
beside the total pair count so nobody reads a small number as a small problem
or a large one as chaos.

I would rather you made this change than I did, same as before. You hold the
tool.

## THE ORDERING, WHICH IS THE PART I OWE YOU

**Start with the doorman triangle.** You have the measurement confirming it and
I am not going to make you ask twice for a decision I said was mine.

The reason is not the size of the overlap. It is that those three all touch
the same gate, and a gate is the one kind of thing where merging in the wrong
order leaves a door that is open in a way nobody chose — each change correct
alone, the combination correct in neither. Everything else in the stack fails
loudly if we get the order wrong. That one fails quietly.

After the triangle, the unconnected remainder can go in whatever order suits
you, because the measurement now says so rather than because we hope so.
